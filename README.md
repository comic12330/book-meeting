综合项目课程实践任务书对应实现。前后端分离：后端 Spring Boot + 原生 MyBatis + MySQL 8.0，前端 Vue 3 + Element Plus。

## 五、用户管理模块

管理端「用户管理」承担任务书基础模块里的**用户管理**职责（必做项「用户模块」只要求注册/登录/资料/角色，用户管理属课程学时分配表中单列的一块）。

### 5.1 权限模型

- 所有 `/api/admin/**` 由 `AuthInterceptor` 统一校验 `role = 1`，接口内不再重复判断，避免漏判。
- **令牌不回传账号状态**：JWT 载荷只携带 `sub`（用户 ID）与 `username`、`role`、`iat`、`exp`，其中 `username`、`role` 只是签发时的快照。若拦截器只验签名，管理员停用或降级某人后，对方手上的旧令牌仍能用满整个有效期，"停用"就只对下一次登录生效。
  因此 `AuthInterceptor` 在验签之后**回查一次数据库**，以库中的 `status`、`role` 为准重建登录上下文：
  - 账号被停用 → 401「账号已被停用，请联系管理员」，旧令牌**立即失效**；
  - 角色被降级 → 后续管理端请求 403，旧令牌**立即失去管理权限**。
  代价是每个请求多一次主键查询，对课设量级可接受；若要优化可加短 TTL 缓存。

### 5.2 业务约束

| 约束 | 原因 |
|---|---|
| 不能停用当前登录的账号 | 避免管理员误操作把自己锁在系统外 |
| 唯一启用管理员不能降级为普通用户 | 降级是让系统失去管理入口的唯一路径（停用自己已被上一条拦住） |
| 账号不可修改、只可停用不可删除 | `meeting_book.user_id` 外键引用用户，物理删除会破坏历史预定记录 |
| 重置密码不校验原密码 | 执行者身份已由管理员权限校验；管理员本就看不到他人原密码 |

### 5.3 重置密码与「密码找回」的关系

两者不冲突：密码找回是**未登录用户证明"我是我"**（验证码/密保），管理员重置是**已登录管理员证明"我有权限"**，最终都落到同一个 `updatePassword(userId, newPassword)`。管理员重置按"管理员指定新密码"实现，不设固定默认值——避免出现"所有人重置后密码都是 123456"的漏洞，也省掉一个 `need_change_pwd` 标记字段。

## 六、业务参数配置

任务书第十一节要求「业务参数不得写死在代码中，会议室容量上限、可选时段、状态码等应通过配置文件或数据表管理」。本项目按参数性质分三层存放，判断标准是「谁需要改它」。

| 层 | 存放位置 | 内容 | 谁能改 |
|---|---|---|---|
| 部署级技术参数 | `application.yml` → `meeting.*` | 数据源、令牌密钥与有效期、分页默认值与上限 | 部署方 / 开发者，改后重启 |
| 业务运营参数 | 数据表 `sys_config` | 单次时长上限、最多提前天数、每日可预定窗口、会议室容量上限 | **管理员在线改，保存即生效，无需重启** |
| 固定业务字典 | Java 常量类 | 预定状态 0–4、会议室状态、角色、密码长度 | 开发者，随代码发布 |

### 6.1 为什么状态码不进配置文件

状态码对应 `status` 列的取值，被 SQL 的 `IN` 条件、审核流程与前端展示共同依赖。改一个值意味着全部历史记录的语义跟着变，它属于「代码与数据共同约定的字典」，不是运营可以随手调整的参数。因此抽成 `BookStatus` / `RoomStatus` / `UserRole` 常量类，作用是消除魔法数字、集中定义；两个「参与冲突判定的状态集合」也放在 `BookStatus` 里，因为它们是状态码的直接派生，分开写容易出现「改了状态码忘改集合」的隐性问题。

### 6.2 sys_config 的管理方式

- 参数项由 `schema.sql` 写入，页面上**只能改值，不能增删键名**——键名是代码里 `SysConfigKey` 枚举声明过的契约，页面新增的键代码读不到。
- 每个参数的类型与取值范围写在 `SysConfigKey` 枚举里（如 `booking.max-hours` 限 1–12），后端保存前校验，管理页的输入控件也从同一份定义取范围，不存在「页面能填、后端拒绝」的口径不一致。
- 读取走内存缓存：首次访问整表加载，管理员保存后直接回写缓存。因此改值**即时生效**，业务校验下一次请求就用新值。若绕过系统直接改库，需打开一次参数页或重启才会同步。
- 跨参数规则单独校验：`booking.daily-start` 必须早于 `booking.daily-end`，两个值分两条记录存，单看一条无法判断。

| 参数键 | 默认值 | 取值范围 | 作用 |
|---|---|---|---|
| `booking.max-hours` | 8 小时 | 1–12 | 一场会议最多占用多久，覆盖「20:00 至次日 02:00」这类跨天场景 |
| `booking.max-advance-days` | 30 天 | 0–90 | 最多提前多久预约；0 表示只接受当天 |
| `booking.daily-start` | 08:00 | — | 每天最早可使用的时刻 |
| `booking.daily-end` | 22:00 | — | 每天最晚可开始的时刻 |
| `room.max-capacity` | 200 人 | 1–1000 | 登记会议室时允许填写的最大人数 |

默认值按真实办公场景设定：一场会议 8 小时已能覆盖全天会议与跨天联调，提前 30 天覆盖到季度会，容量 200 人覆盖报告厅，再大的数值对会议室管理没有实际意义。

「每日窗口」只约束**开始时刻**，结束时刻允许跨到次日——任务书要求支持 20:00 至次日 02:00 这类跨天场景，若把结束也限制在同一天窗口内，跨天就提交不了了。结束时间靠「跨度上限」间接约束。

## 七、核心业务：时段冲突校验

判定条件（`MeetingBookMapper.xml` → `countConflict`）：

```sql
SELECT COUNT(1) FROM meeting_book
WHERE room_id = #{roomId}
  AND status IN (0, 1)              -- 提交环节：待审核、已通过 都算占用
  AND start_time < #{endTime}       -- 已有记录开始 早于 新预定结束
  AND end_time   > #{startTime}     -- 已有记录结束 晚于 新预定开始
```

设计要点：

1. **两次校验**：`BookService.submit()` 提交时校验一次；`BookService.approve()` 审核通过时再校验一次（排除自身 id）。因为两条待审核记录可能时段重叠，先通过的那条占位后，后一条若不再校验就会被放进系统。
2. **两次校验的"有效状态"不同**：提交时 `status IN (0,1)`（待审核也算占用，防止同一时段被反复提交）；审核时只算 `status = 1`（已通过）。若审核时也把待审核算进来，两条重叠的待审记录会互相阻断、谁都无法通过——这是本项目踩过并修掉的一个坑。
3. **审核串行化**：审核通过前先 `SELECT id FROM meeting_room WHERE id = ? FOR UPDATE` 锁住会议室行，把同一会议室的审核串行执行，避免两个管理员同时点「通过」各自校验都通过、结果双双入库。锁随 `@Transactional` 在方法结束时释放。
4. **判定交给数据库**：用 `COUNT` 一次算完，不在 Java 里先查再比，缩小并发窗口。
5. **索引**：`meeting_book` 上建 `idx_book_room_start (room_id, start_time)`，冲突查询走该索引。
6. **跨天支持**：起止时间都是 `datetime`，用 `LocalDateTime` 比较，20:00–次日 02:00 可正常判定。
7. **后端独立校验**：`checkTimeRange()` 校验结束晚于开始、不早于当前时刻、单次跨度不超上限、开始时刻落在每日可预定窗口内，且不超出最多提前天数；阈值全部读 `sys_config`，不依赖前端时间控件。

## 八、定时任务：已结束预定自动完成

使用时间已结束、状态仍为「已通过」的记录，由定时任务周期置为「已完成」（1 → 4）：

```sql
UPDATE meeting_book SET status = 4
WHERE status = 1 AND end_time < NOW()
```

| 项 | 取值 |
|---|---|
| 调度方式 | `@EnableScheduling` + `@Scheduled`，间隔在 `application.yml` 的 `meeting.task.complete-expired-cron`，默认每 5 分钟 |
| 代码位置 | `task/BookStatusTask`（何时跑） + `BookService.completeExpired`（做什么） |
| 手动触发 | `POST /api/admin/books/complete-expired`，与定时任务共用同一个 service 方法，便于验证与演示 |
| 时间基准 | 数据库 `NOW()` |

四个刻意做成这样的点：

1. **不复用 `updateStatus`**：那条语句会重写 `audit_msg` 与 `audit_time`。定时任务手里没有审核意见，传 null 会把「谁、何时、以什么理由审批」清空，历史可追溯性就断了。这里单独写一条只改 `status` 的 UPDATE。
2. **时间基准交给数据库**：`create_time` 由 `DEFAULT CURRENT_TIMESTAMP` 生成，用 `NOW()` 比较保证两侧同一时钟源；改在 Java 里取当前时间，JVM 与 MySQL 时区不一致时会出现「刚提交就被判为已结束」。
3. **幂等，不需要分布式锁**：更新过的记录状态已是 4，不再命中 `status = 1`，重复执行影响 0 行；多实例并发也只是后到的影响 0 行。
4. **不需要补跑机制**：判定条件基于数据本身，而不是「上次执行到哪」，停机期间漏掉的记录由下次启动后的第一次执行自动补齐。跨天会议（19:00 → 次日 02:00）无需特殊处理。

配套改动：`audit()` 增加一条校验——使用时间已结束的申请不能再「通过」。否则通过后下一轮任务立刻把它变成已完成，状态等于从「待审核」直接跳到「已完成」，中间那一步在历史里看不见。**只拦「通过」不拦「驳回」**：驳回是清理过期待审队列的唯一出口，若一并拦住，这些记录就只能进数据库手改。

## 九、操作日志

用于事后追查「谁在什么时候改了全站数据」。**只记录管理端的数据变更动作**（增、删、改），普通用户的提交、取消、改资料不记录——他们只影响自己的数据，且 `meeting_book`、`user` 表本来就带 `user_id` 与时间戳；本功能防的是管理员误改或破坏全站数据，不是做用户行为分析。

### 9.1 记录范围

| 模块 | 动作 |
|---|---|
| 会议室 | 新增、编辑、删除 |
| 预定审核 | 审核通过、审核驳回、取消他人预定 |
| 用户管理 | 新增、编辑、启停用、重置密码 |
| 公告管理 | 发布、编辑、删除 |
| 系统参数 | 修改参数 |

操作人、操作类型、操作时间三项必留，另外记录结果与失败原因——「被拒绝的越权尝试」比成功流水更有追查价值。

### 9.2 实现方式

`@LogOperation(type = ..., target = ...)` 标在 Service 的写方法上，由 `OperationLogAspect` 环绕拦截。**不按 URL 猜动作**：审核通过与驳回是同一个接口，按路径无法区分。

四个关键点：

1. **操作人在主线程快照**：`UserContext` 是 ThreadLocal，一旦交给异步线程就读不到。切面在进入方法前把用户与 IP 存进局部变量。`LoginUser` 为此补了 `realName`（不进令牌载荷，由拦截器回查数据库时填上），日志里存姓名而不是登录账号。
2. **成功日志在事务提交后写**：注册 `afterCommit` 回调。与业务同事务会在回滚时一起消失；独立事务先提交又会出现「日志说有、业务表没有」。
3. **失败日志立即写**：`OperationLogService.record` 用 `REQUIRES_NEW` 挂起外层事务独立提交，业务回滚后这条记录仍在。只记业务拒绝类原因（时段冲突、不能停用自己），参数格式错误在进入方法前就被拦下，不产生噪声。
4. **日志写失败不影响业务**：切面 catch 后只打告警。让一次日志异常导致用户提交预定失败，是本末倒置。

对象描述用 SpEL 取：`describe(#bookId)` → 「第二会议室 2026-11-21 09:00 至 11:00」。删除、启停用这类只拿到主键的方法，靠调用业务对象的公开方法换出可读名称。

### 9.3 表结构的三个取舍

- **操作人姓名存快照**，不连 `user` 表：日志要回答「当时是谁」，用户改名或调岗后历史不能被追溯修改。
- **不加指向 `user` 的外键**：日志属审计数据，不能因为用户状态变化插不进去。`meeting_book` 加外键是在防脏数据，两者目的不同。
- **只有查询接口，没有改和删**：审计日志能被修整就等于没有。

### 9.4 顺带修掉的两个缺陷

联调这个功能时在 `cancel` 里发现两处问题，一并修了：

1. **取消会抹掉审核痕迹**。取消原先复用 `updateStatus` 并传 `auditMsg = null`，「审核通过 → 取消」的记录在取消后丢失 `audit_time`，通过时填过意见的连意见也丢。现在单独写 `cancelById`，只更新 `status`、`cancel_reason`、`cancel_time`，与 `completeExpired` 的处理口径一致。
2. **管理员取消他人预定是一条隐形权限**。`cancel` 里显式放行了 `isAdmin()`，但管理端没有入口、不留理由、没有痕迹，只能靠 curl 调。现在收口为 `PUT /api/admin/books/{id}/cancel`：理由必填并落库（申请人可在「我的预定」看到「管理员取消：xxx」），动作记入日志；用户端接口恢复为只能取消本人。

行政取消权本身保留——员工离职、会议室临时征用、接待需要清场，都属于「本人联系不上但会议室还被占着」的情形，收回权限就只能进数据库手改。

**三个设计要点**

1. **时间槽在运行时生成，不写死日期**。`00-1` 算出一整天互不重叠的时段（1~20 天后的某一天）写进集合变量，后续用例全部引用。写死日期第二天就全过期，而且第二次运行必然撞上上一轮留下的记录。
2. **令牌自动传递**。登录请求的 Tests 里把 token 写进集合变量，后续请求用 `{{userToken}}` / `{{adminToken}}` 引用，不需要手工复制粘贴；单独调试某条请求时，先跑一次对应角色的登录即可。
3. **断言写在请求的 Tests 里**。每条请求都有 `pm.test(...)`，跑完在「Tests」标签页直接看到逐条通过情况，Runner 汇总页可以截图作为报告素材。

**一处需要知道的环境依赖**：`04-15` 要求库里有一条「已结束但仍待审」的记录（现取 `meeting_book.id = 2`），而这条记录同时满足定时任务的归档条件（状态为已通过且已结束），可能先被置为「已完成」。两种情况后端都会拒绝审核，只是提示语从「已结束」变成「已处理」，因此该用例断言的是「审核被拒绝且提示明确」，不锁死具体文案。跑之前可执行：

## 十二、可直接作为拓展项继续做的功能

任务书列出的 9 项拓展里，**定时任务**（第八节）与**操作日志**（第九节）已实现，其余条目中以下 4 项与本项目结构契合度最高，按任务书标注的星级从低到高排列：

| 星级 | 拓展项 | 改动落点 |
|---|---|---|
| ★★★ | 日历视图展示会议室占用情况，直观呈现空闲时段 | 新增 `GET /api/books/calendar`，`MeetingBookMapper` 加按 `room_id` + 时间区间的查询（走现有 `idx_book_room_start`）；前端用 `el-calendar` 的 `#date-cell` 插槽，或自绘「日期 × 时段」网格 |
| ★★★☆ | 按月统计各会议室使用频次与使用率，ECharts 可视化 | 新增 `GET /api/admin/stats/monthly`，一条 `GROUP BY room_id` 的聚合 SQL（次数 + 总分钟数）；前端 ECharts 柱状（频次）+ 折线（使用率）双 Y 轴 |
| ★★★☆ | 密码找回与用户头像上传 | `user` 表加 `avatar` 列；新增 `POST /api/user/avatar` 存本地目录，`WebConfig` 加 `addResourceHandlers` 暴露静态路径 |
| ★★★★ | 对频繁取消或恶意预定的用户实施提交限制 | 阈值进 `sys_config`；`BookService.submit()` 开头加一道统计校验，与时长、提前天数等现有校验并列 |

三项口径要先定，否则做出来会和现有规则打架：

- **日历必须区分待审与已通过**：提交时的冲突判定是 `status IN (0,1)`（`BookStatus.occupiedOnSubmit()`），日历若只画「已通过」，用户会看到一片空闲却提交被拒。建议待审用浅色、已通过用深色，驳回/取消/完成不占位。
- **使用率的分母**：`当月已过天数 × (每日最晚开始 − 最早开始)`，两个时间从 `sys_config` 取，不能写死 8 小时。分子只统计 `status IN (1,4)`（真正占用了会议室），待审、驳回、取消都不计入。
- **密码找回没有现成通道**：项目没接邮件或短信服务。现实的两条路是①注册时设「安全问题」，找回时校验答案；②沿用已有的「管理员重置密码」入口。硬做邮箱验证码要引 JavaMail 加 SMTP 配置，演示时最容易翻车的就是收不到信。

「频繁取消」建议先用单一维度：近 30 天 `status = 3`（已取消）的次数超过阈值即拒绝提交，本人取消与管理员取消都计入。不建议一开始就把「被驳回次数」也算进去——驳回本身含审核员的主观判断，两个维度叠加容易误伤正常用户。

另有一项不属于任务书拓展、但属可续的优化方向：**日志保留期清理**。日志只增不减，长期运行会持续膨胀，可加 `log.keep-days` 参数（默认 90 天）放进 `sys_config` 由管理员调整，再用定时任务定期删除过期记录。没有立即做，是因为答辩周期内数据量级不足以暴露问题，且清理任务本身有误删风险。

## 十三、注意事项

- **改了后端代码要重启**：`BookService` / Mapper 的修改不会热生效（工程未装 devtools），IDEA 里停止后重新运行 `MeetingRoomApplication`。
- 密码摘要用 MD5：任务书允许「BCrypt 或 MD5」，选 MD5 是为了建库脚本能离线一次执行。若要升级 BCrypt，只改 `Md5Util` 的 `encode`/`verify` 实现，调用方无需改动（数据库 `password` 字段已是 VARCHAR(64)，足够存 BCrypt 的 60 位）。
- 业务参数分三层管理：技术参数在 `application.yml`，运营参数在 `sys_config` 表（管理员在「系统参数」页在线改，即时生效），固定字典（状态码、角色、密码长度）在 Java 常量类。代码里不再有散落的魔法数字，详见第六节。
- 设备类型（投影仪 / 麦克风 / 视频会议终端）目前定义在前端 `utils/dict.js` 与会议室表的 `equipment` 字段约定中，若要支持管理员自行增减设备类型，需要再加一张设备字典表。
- 删除会议室时若有历史预定记录会被拒绝，引导改为「停用」，避免破坏历史数据。
